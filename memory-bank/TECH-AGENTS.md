# FACt.Smack 기술 스택 및 개발 구조 규칙

> 이 문서는 FACt.Smack을 유지보수 가능한 웹 서비스로 개발하기 위한 기술 선택과 코드 구조의 기준이다.
> 제품·안전 정책은 `service-design-rule.md`를 우선하며, 기술 결정은 그 정책을 침해해서는 안 된다.

## 1. service-design-rule.md 동기화 계약

- `service-design-rule.md`는 제품 목적, 정책, 도메인 규칙의 **단일 기준 문서**이며, 이 문서는 이를 구현하는 기술 기준이다.
- `service-design-rule.md`가 변경되면, 먼저 변경 항목이 인증·권한·데이터 모델·API·이미지 처리·운영·UI·테스트·배포에 미치는 영향을 분석한다.
- 영향이 있으면 해당 기술 규칙과 구현 계획을 즉시 갱신한다. 영향이 없더라도 `TECH-AGENTS.md`의 결정 기록에 검토 완료 사실을 남긴다.
- 두 문서는 같은 작업 흐름에서 함께 커밋한다. 서비스 규칙과 기술 규칙이 충돌하면 서비스 규칙을 우선하고, 코드는 보류한 뒤 기술 문서를 맞춘다.
- 기능 구현 전에는 두 문서의 최신 변경 기록을 확인한다.

## 2. 기본 원칙

- 프론트엔드는 **HTML, CSS, JavaScript**로 작성한다.
- UI는 **React 컴포넌트**로 구성하며, JSX를 사용한다.
- JavaScript를 기본 언어로 사용한다. 공개 함수·API 데이터·복잡한 객체에는 JSDoc으로 계약을 명시한다.
- 모든 애플리케이션 소스 파일은 파일 상단에 `정의:` 주석으로 책임을 적는다. 컴포넌트·함수·상수·자료구조에는 책임, 입력·출력 또는 제약을 설명하는 JSDoc/언어 주석을 붙인다. 자명한 JSX·CSS 속성을 반복 설명하는 주석은 금지한다.
- 기본 UI 폰트는 한글 **Pretendard Variable**, 영어·라틴 문자·숫자 **Inter Variable**이다. Neutral Sans Serif 기반을 유지하고, UI에 장식적 세리프 서체를 추가하지 않는다.
- 모든 UI 작업은 한국어(`ko`)와 영어(`en`)를 동시에 완료해야 한다. 메뉴·버튼·오류·빈 상태·모달·토스트·날짜·수량·단위·통화·접근성 라벨까지 메시지 키 기반 국제화 대상으로 관리한다.
- 신규 컴포넌트는 `ko`/`en` 두 환경에서 문구 누락, 줄바꿈, 넘침, 버튼 크기, 키보드·스크린리더 라벨을 검증한 뒤에만 완료로 판정한다. Material Symbols와 같은 아이콘 폰트는 본문 영문 폰트 규칙과 분리해 ligature가 텍스트로 노출되지 않게 한다.
- DOM 사후 치환은 목업 검증을 위한 임시 호환만으로 제한하고, 실서비스 전환 전에는 컴포넌트 내 하드코딩된 표시 문구를 모두 중앙 i18n 메시지 키로 이관한다.
- 기능 UI 타이포그래피는 하단 메뉴·필터·보조 행동을 **최소 11~12px**, 주요 버튼과 입력을 **14~16px**, 카드의 핵심 질문을 **24px / 30px**로 사용한다. 10px 이하 표기는 법적 고지처럼 대체 수단이 있는 비핵심 정보에만 제한한다.
- 반응형은 `dvh` 기반의 실제 가용 화면을 기준으로 한다. 스마트폰(`max-width: 767px`)은 `width: 100%` 전체 폭을 사용하고, 태블릿·PC(`min-width: 768px`)는 최대 640px 중앙 콘텐츠 컬럼을 사용한다. 헤더·하단 메뉴는 고정하며, 메인 피드와 카드는 `flex: 1`·`min-height: 0`으로 남는 가용 높이를 정확히 채운다.
- Feed는 화면 고정형(`overflow: hidden`)으로 유지하고, Upload·Ranking·Profile은 본문 컨테이너에만 `overflow-y: auto`를 부여한다. 고정 하단 메뉴 높이와 안전 영역을 본문 `padding-bottom`에 반영해 마지막 조작 요소가 가려지지 않게 한다.
- 피드 미디어는 카드의 상단 미디어 영역에서 `object-fit: contain`으로 렌더링하고, 평가·댓글 제어는 별도 하단 상세 영역에 둔다. 다중 미디어에는 38~46px 폭의 좌·우 미리보기와 280ms 이하의 방향 반동을 사용하며, 중앙 미디어의 레이아웃 폭을 줄이지 않는다.
- 모든 화면 크기에서 카드의 잘림·내부 스크롤·카드와 고정 헤더/하단 메뉴 사이의 비의도적 여백을 회귀 테스트한다. 브라우저 UI 표시·숨김, 안전 영역, 회전, 키보드 노출 상태를 포함한다.
- 피드 제스처는 입력 장치별로 분리한다. PC 휠과 모바일 세로 스와이프는 카드 목록을, 좌·우 스와이프는 현재 카드의 `Media[]` 인덱스를 이동한다. 우측 화살표는 모든 환경에서 카드 목록을 이동하며, 앨범 막대는 버튼으로 구현해 키보드·스크린리더도 특정 미디어를 선택할 수 있어야 한다.
- 구현은 모바일 우선, 접근성 우선, 테스트 가능성을 우선한다.
- 화면 컴포넌트가 데이터 저장·권한 검증·직접 HTTP 호출을 동시에 담당하지 않는다.
- 비밀값, API 키, 관리자 권한은 브라우저 코드와 Git 저장소에 절대 넣지 않는다.

## 3. 프론트엔드 표준 스택

| 영역 | 표준 선택 | 사용 규칙 |
| --- | --- | --- |
| 빌드·개발 서버 | Vite | 새 프론트엔드는 Vite의 React 템플릿으로 시작한다. |
| UI | React + JSX | 함수형 컴포넌트와 Hooks만 사용한다. 클래스 컴포넌트는 사용하지 않는다. |
| 공통 UI 프리미티브 | shadcn/ui + Google Material UI (선별 병행) | 서비스의 다크·네온 디자인 토큰과 화면 구조를 변경하지 않는 범위에서 병행한다. shadcn/ui는 코드 소유권과 접근성 동작이 필요한 Dialog·Sheet·Select·Toast 등에, Material UI는 관리자 화면의 Data Grid·복잡한 폼·날짜 선택 등 생산성이 높은 요소에 우선 사용한다. |
| 라우팅 | React Router | 페이지 URL과 접근 권한 경계를 명시한다. |
| 스타일 | CSS Modules + 전역 CSS 변수 | 컴포넌트별 스타일은 CSS Module로 격리하고, 색상·간격·타이포그래피는 CSS 변수로 통일한다. |
| 서버 상태 | TanStack Query | API 조회·캐시·재시도·무효화는 Query 계층에서 관리한다. |
| 클라이언트 상태 | React Context + useReducer | 인증 UI, 모달 등 전역 UI 상태에만 사용한다. 서버 데이터를 전역 상태에 중복 저장하지 않는다. |
| 폼 | React Hook Form + Zod | 업로드·신고·로그인 폼의 입력 검증과 오류 표시를 통일한다. |
| 테스트 | Vitest + React Testing Library | 사용자 행동 중심의 단위·컴포넌트 테스트를 작성한다. |
| 품질 | ESLint + Prettier | 포맷·정적 분석은 CI에서 강제한다. |

## 4. 프론트엔드 디렉터리 구조

```text
src/
├── app/                 # 앱 부트스트랩, Provider 조합, 전역 설정
├── routes/              # 페이지 라우트와 접근 제어
├── pages/               # 라우트 단위 화면 조합
├── features/            # 도메인 기능 단위 모듈
│   ├── auth/
│   ├── feed/
│   ├── posts/
│   ├── votes/
│   ├── ranking/
│   ├── profile/
│   └── moderation/
├── components/          # 여러 기능에서 재사용하는 UI 컴포넌트
│   ├── ui/              # Button, Input, Modal 등 원자 컴포넌트
│   └── layout/          # Header, BottomNavigation, PageLayout
├── services/            # API 클라이언트와 외부 연동 어댑터
├── hooks/               # 재사용 Hook
├── lib/                 # 순수 유틸리티, 상수, JSDoc 타입
├── styles/              # reset, tokens, 전역 스타일
├── assets/              # 앱에 포함되는 정적 리소스
└── test/                # 테스트 설정·공통 도우미
```

- `features/<feature>/components`, `hooks`, `api.js`, `schemas.js`, `*.test.jsx`를 기능 안에 함께 둔다.
- `pages`는 기능을 조합만 하며, 비즈니스 로직을 직접 구현하지 않는다.
- `components/ui`는 도메인(Post, Vote 등)을 알지 못해야 한다.
- shadcn/ui와 Material UI를 병행할 때에도 한 화면의 동일한 역할에 두 라이브러리를 섞어 쓰지 않는다. 디자인 토큰·색상·타이포그래피·여백·상태 표현은 FACt.Smack 기준을 우선한다.
- 사용자용 화면은 shadcn/ui를 우선하고, Material UI는 관리자 화면의 Data Grid·복잡한 폼처럼 도입 이점이 분명한 요소에 우선한다. 예외 도입 시에는 이유와 시각적 동등성 검증 결과를 결정 기록에 남긴다.
- `services`만 HTTP 클라이언트를 직접 호출한다.
- 한 파일은 하나의 명확한 책임을 갖고, 250줄을 넘기기 시작하면 분리 여부를 검토한다.

## 5. React·HTML·CSS 작성 규칙

- 시맨틱 HTML(`main`, `nav`, `button`, `label`, `form`)을 우선 사용한다.
- 클릭 가능한 요소에 `div`를 쓰지 않으며, 키보드 조작과 포커스 상태를 제공한다.
- 모든 이미지에는 의미에 맞는 `alt`를 제공한다. 장식 이미지는 빈 `alt`를 사용한다.
- 컴포넌트 Props는 JSDoc으로 입력·출력·필수 여부를 설명한다.
- 인라인 스타일은 테마 색상처럼 런타임 값이 꼭 필요할 때만 사용한다.
- 색상, 간격, z-index, 브레이크포인트는 CSS 변수 또는 공통 토큰으로 관리한다.
- API 요청 상태는 반드시 loading, empty, error, success 상태를 모두 보여 준다.
- 브라우저 localStorage는 UI 설정·임시 초안에만 사용한다. 사용자 콘텐츠·권한·투표의 원본 데이터로 사용하지 않는다.

### 현재 프로토타입 전환 상태

- 현재 실행 화면은 `index.html`이 `src/main.jsx`를 로드하는 Vite + React 앱이다. 과거 Vanilla JavaScript 프로토타입은 Git 이력과 `memory-bank/archive/`에서만 참고한다.
- React 화면의 사용자 수동 검증 기록은 `progress.md`에 남기며, 신규 화면·상호작용은 해당 기준을 갱신한 뒤 구현한다.
- 현재 UI에서 카테고리 색상처럼 카드 데이터에 따라 달라지는 값만 인라인 스타일로 적용한다. YES는 채움형 주 동작, NO는 같은 색상의 윤곽선형 보조 동작으로 유지한다.
- 카드 컨테이너의 기본 라운드는 `rounded-xl` 수준으로 제한한다. 버튼·입력 요소는 조작 대상임을 구분하기 위해 필요한 범위의 라운드를 유지할 수 있다.

## 6. 기능별 책임

| 기능 | 책임 | 금지 사항 |
| --- | --- | --- |
| auth | 로그인 상태, 보호 라우트, 세션 만료 UI | 토큰을 localStorage에 직접 저장 |
| posts | 사진 선택, 업로드 상태, 게시물 조회·삭제 UI | 브라우저에서 이미지 공개 URL을 임의 생성 |
| votes | 카드당 투표 UI, 결과 갱신 | 클라이언트에서 최종 득표 수 확정 |
| feed | 필터·페이지네이션·카드 표시 | 권한 판단을 UI만으로 처리 |
| ranking | 서버가 제공한 랭킹 표시 | 클라이언트에서 랭킹 공식을 중복 계산 |
| moderation | 신고 작성·상태 조회 | 일반 사용자에게 운영자 데이터 노출 |
| admin | 관리자 전용 설정, 회원·역할·제재 관리, 카테고리 관리, 이미지 처리 정책·작업 상태 | 일반 사용자 라우트에서 관리자 API 호출 또는 권한 없는 설정 변경 |

## 7. 백엔드 도입 기준과 확정 스택

현재 localStorage 프로토타입을 넘어 실제 사용자·사진·투표를 다루기 시작하면 백엔드가 **필수**다. P1 정책(공개 범위, 익명성, 사진 권리·연령, 검토 흐름)을 확정한 뒤 아래 스택으로 전환한다.

| 영역 | 확정 스택 | 역할 |
| --- | --- | --- |
| 백엔드 플랫폼 | Supabase | Postgres, Auth, Storage, Edge Functions, 로그를 일관되게 제공 |
| 데이터베이스·마이그레이션 | Supabase Postgres + Supabase CLI SQL migrations | User, Post, Vote, Aggregate, Report 등 영구 데이터와 스키마 변경 관리 |
| 인증 | Supabase Auth | Apple·Google·Kakao·이메일 로그인, 세션·계정 연결의 기반 |
| API·권한 작업 | Supabase Edge Functions | 권한 있는 쓰기·운영 처리·외부 연동. 클라이언트 직접 DB 쓰기를 금지 |
| 파일 저장소 | Supabase Storage | 이미지·동영상 원본·파생본 저장, 짧은 수명 signed URL 발급 |
| 접근 제어 | Postgres RLS + Storage 정책 | 사용자·팔로워·운영자·관리자별 최소 권한 강제 |
| 비동기 미디어 작업 | 별도 워커(추후 구현 시 선택) | 이미지 검사·변환, 동영상 검사·파생본·썸네일. Edge Function의 실행 한도에 의존하지 않음 |
| 캐시·속도 제한 | Edge Function + 필요 시 관리형 Redis | 투표·업로드 보호와 짧은 수명 캐시. 실제 도입 시 별도 결정 |
| 관측성·배포 | Supabase 로그 + Vercel + 오류 추적 | 환경 분리, 오류·보안 이벤트·운영 경보 |

### 백엔드 디렉터리 구조

```text
src/
├── lib/supabase/        # 브라우저 클라이언트, 타입, 호출 어댑터
├── features/            # 화면별 UI·상태·서비스 호출
└── services/            # Supabase 호출을 감싼 도메인 서비스
supabase/
├── migrations/          # Postgres SQL 마이그레이션과 RLS 정책
├── functions/           # 권한 있는 Edge Functions
└── seed.sql             # 개발용 데이터
workers/media/           # 이미지·동영상 검사·변환 워커(도입 시)
```

## 8. API·데이터 구현 규칙

- 모든 쓰기 작업은 Supabase RLS 정책과 Edge Function의 인증·인가·입력 검증·감사 로그를 함께 거친다.
- 인증은 Supabase Auth를 통해 Apple·Google·Kakao OAuth/OIDC와 이메일 방식을 지원한다. 제공자 비밀값은 Supabase secrets에만 주입하고, 제공자 ID와 이메일 충돌은 명시적 계정 연결 절차로 처리한다.
- 개인 계정 설정 API는 프로필·인증 수단 연결·알림·기본 게시물 설정·차단 목록·탈퇴 요청을 분리하고, 민감한 변경은 재인증과 감사 로그를 적용한다. 관리자 역할·운영 설정은 일반 사용자 설정 API에서 절대 노출하지 않는다.
- `POST /posts`, `POST /posts/:id/votes`, `POST /reports`는 idempotency key를 지원한다.
- `Vote`에는 `(postId, voterId)` 유니크 제약을 둔다.
- Post는 최대 이미지 5개와 동영상 1개(최대 10초)의 정렬된 Media를 가질 수 있으며, 각 이미지·동영상의 처리 상태와 파생본을 독립적으로 관리한다.
- Media에는 게시물 내 정렬 순서(`sortOrder`)를 저장한다. 업로더의 순서 변경은 대표 미디어와 캐러셀 순서에 즉시 반영하고, 서버는 최대 이미지 5개·동영상 1개 제약을 최종 검증한다.
- Comment는 parentCommentId를 선택적으로 가지며, 서버가 깊이 1까지만 허용한다. 댓글 조회 API는 요약 2~3개와 전체 확장 페이지네이션을 분리하고, 댓글 허용 여부·게시물 공개 범위·차단 상태를 모두 인가에 반영한다.
- 게시물·댓글 삭제 API는 모두 소프트 삭제로 처리한다. 운영자는 숨김만 수행하고, 관리자는 신고 검토 후 삭제 조치를 수행할 수 있으며, 소프트 삭제 콘텐츠는 별도 권한 관리자만 admin 화면에서 열람한다. 모든 상태 전이는 감사 로그에 기록한다.
- 업로드 자격은 서버가 판정한다. 초기에는 모든 로그인 회원에게 허용하되, 이후 활동 기준 전환은 관리자 설정·감사 로그·사용자 안내를 거쳐 활성화하며 클라이언트 조건만으로 우회할 수 없게 한다.
- 이미지·동영상 업로드는 Supabase Storage의 짧은 수명 signed upload URL을 이용하며, 형식·크기·메타데이터·악성 파일 검사를 거친다.
- 동영상은 초기 정책상 10초 이하만 허용한다. 클라이언트는 선택 직후 메타데이터로 길이를 안내하되, 서버·비동기 작업이 신뢰 가능한 미디어 검사 결과로 길이 제한을 최종 강제한다.
- 객체 키는 `uploads/{UTC-YYYY}/{MM}/{DD}/{image|video}/{postId}/{assetId}/{original|derivatives/...}` 규칙을 사용한다. 사용자 ID·이메일·핸들은 경로에 넣지 않으며, 목록·검색·보존은 DB의 Media 레코드로 처리한다.
- 업로드 완료 후 비동기 작업이 이미지의 모바일용 파생본과 동영상의 안전한 재생 파생본·썸네일을 생성한다. 관리자 설정에는 미디어별 허용 형식, 최대 업로드 용량, 최대 해상도·재생 시간·목표 용량·품질 정책을 둔다.
- 카테고리는 ID, 표시명, 색상 토큰, 상태(active/hidden/archived), 정렬 순서, 생성·수정 주체와 시각을 저장한다. 삭제는 참조 Post가 없을 때만 허용하고, 그 외에는 숨김 또는 보관으로 처리한다.
- 관리자 API는 별도 권한 미들웨어와 감사 로그를 사용한다. 카테고리 정렬 변경은 순서 충돌을 막기 위해 트랜잭션으로 처리한다.
- 회원관리 API는 최소 권한과 최소 정보 노출 원칙을 적용한다. 역할·계정 상태·제재 변경은 사유, 대상, 변경 전후 값, 처리자를 감사 로그에 남기고 자기 자신의 관리자 권한을 임의로 변경할 수 없게 한다.
- `Aggregate`는 서버에서 계산하고, 필요하면 비동기 재계산 가능한 구조로 만든다.
- API 응답·오류 형식은 기능별로 임의로 바꾸지 않고 공통 계약을 사용한다.
- DB 스키마 변경은 마이그레이션, 데이터 백필 계획, 롤백 계획을 함께 제출한다.

## 9. 보안·품질 게이트

- 환경 변수는 `.env.example`에 키 이름만 기록하고 실제 값은 비밀 관리 시스템에 저장한다.
- CORS, CSRF, 속도 제한, 요청 크기 제한, 업로드 검증을 기본 활성화한다.
- 권한 검증은 라우트·서비스 계층에서 수행하며 프론트엔드 표시에 의존하지 않는다.
- 관리자 웹은 일반 사용자 웹과 별도 도메인·배포 환경·Git 저장소·개발 디렉터리로 분리한다. 초기 Google 최고 관리자 allowlist는 인증 제공자 subject ID 등 비밀 관리 설정으로만 주입하며, 하위 관리자 권한 변경은 서버 인가와 감사 로그를 거친다.
- 새 기능은 최소한 정상 흐름, 권한 거부, 입력 오류, 네트워크 오류를 테스트한다.
- PR은 lint, 테스트, 빌드를 통과해야 병합할 수 있다.
- 기능 단위가 아닌 계획 단계 단위로도 사용자 수동 검증을 수행한다. `feature-backlog.md`의 해당 단계가 사용자에게서 `적합` 판정을 받기 전에는 다음 단계 코드를 시작하지 않는다.
- 사용자 수동 검증 링크는 사용자가 `로컬에 라이브해줘`라고 명시 요청할 때만 생성한다. 이때 이전 서버와 다른 고유 Vite 포트를 사용하고, URL에는 변경 식별 쿼리를 붙인다. 링크 전달 전 `curl` 등으로 최신 소스 모듈의 핵심 변경 문자열을 확인하며, 기존 탭·포트 링크를 재사용하지 않는다. 코드 변경·빌드 성공만으로 Chrome을 자동 실행하지 않는다.
- main 브랜치에 직접 배포하지 않고, 개발·스테이징·운영 환경을 분리한다.

## 11. 문서 갱신 규칙

- `service-design-rule.md` 변경은 항상 이 문서의 기술 영향 분석과 갱신을 동반한다.
- 기술 선택을 추가·교체하거나 구조 규칙을 바꾸면 이 파일과 `service-design-rule.md`를 같은 변경에서 갱신한다.
- 외부 의존성을 추가할 때는 목적, 데이터 접근 범위, 제거 방법을 PR 설명에 기록한다.
- 사용자가 커밋·푸시를 요청했거나 작업 완료 시 커밋·푸시를 지시한 범위에서는, 추가 확인 없이 해당 프로젝트의 현재 브랜치에 즉시 커밋·푸시한다. 단, Git·운영체제·호스팅 서비스가 요구하는 권한 승인 창은 우회하지 않는다.
- 브랜치 배포 게이트는 `facs` 우선이다: 로컬 검증본을 먼저 `facs`에 커밋·푸시하고, 사용자의 수동 `적합` 판정 뒤에만 `main` 반영 여부를 묻는다. 사용자가 `main` 반영을 명시 승인하면 `facs`의 검증된 커밋을 `main`에 병합·푸시한다. `main`에 로컬 변경을 먼저 커밋하거나 푸시하지 않는다.
- 브랜치 수를 줄이기 위해 과제 단위의 단일 브랜치를 유지하고, 작은 후속 수정은 같은 미병합 브랜치에 누적한다. 병합된 브랜치는 자동 삭제하지 않으며, 운영 확인 뒤 복구 태그를 남긴 후 최소 30일 보관한다. 삭제는 사용자 명시 승인으로만 가능하다.
- 사용자 기능의 새 API·데이터·상태를 추가할 때는 관리자 화면과 API에 필요한 설정, 조회, 제어, 모니터링, 감사 로그를 함께 설계하고 `feature-backlog.md`의 ADM 항목을 갱신한다.
- 운영 정책의 재검토 결과가 서비스 규칙에 반영되면, 인증·권한·데이터·API·관측성·테스트 영향 여부를 확인하고 그 결과를 이 문서의 결정 기록에 남긴다.
- P1/P2 정책 미결정으로 구현이 막히면 `🚨 개발 결정 필요` 알림을 먼저 표시한다.
