## 재현된 불필요한 전송과 수정

기존 `CardMedia`는 화면의 video 외에 `createRemoteVideoPoster()`에서 숨은
video를 생성하여 같은 signed URL을 preload=auto로 별도 요청했다. URL 변경이나
카드 재마운트 시 별도 포스터 요청을 다시 시작할 수 있는 구조였다.

외부 Supabase 원본을 요청하지 않고 localhost에서 939바이트짜리 합성 WebM을
생성했다. 동일 파일을 Cache-Control: no-store로 제공하고 서버에서 미디어 요청과
바디 크기를 집계했다. 기존 함수는 수정 전 저장소 소스에서 읽어 비교에 사용했다.

| 비교 | 요청 | 바디 전송 | 포스터 생성 | readyState |
| --- | --- | --- | --- | --- |
| 기존 화면 + 숨은 포스터 영상 | 2 | 1,878 bytes | 성공 | 4 |
| 실제 화면의 디코딩된 프레임 재사용 | 1 | 939 bytes | 성공 | 4 |

이는 이 로컬 cold/no-store 비교에서 50% 감소한 결과이며, 브라우저 캐시·Range
정책이 다른 운영 전체 전송량을 50% 줄인다는 주장이나 과거 초과분의 기여도는 아니다.

수정은 기존 video의 loadeddata에서 canvas로 포스터를 만들고, 별도 video·원격
load·타임아웃을 제거한다. 메모리용 포스터는 긴 변 최대 640px로 제한하지만 사용자
동영상 원본·업로드 크기·재생 해상도는 변경하지 않는다. 캡처 불가 시 native 재생은
유지한다. URL이 바뀌면 이전 포스터를 표시하지 않는다. iframe/외부 CDN/추적·유료
기능·업로드 제한·캐시 TTL 변경은 추가하지 않는다.

## 2026-10-19 후속 — OPS-03C 실제 서명·HEAD 최소 확인

사용자가 후속 진행을 승인했다. staging target guard 통과 후
`zvaheyfumpmzrolsbtrf`에서 앱과 같은 publishable/anon 권한만 사용했다.
공개 로그인 배경 RPC가 반환한 객체 1개를 선택했으며 계정 로그인, service role,
권한 변경, DB/객체 변경은 하지 않았다. 경로·키·서명 token은 출력/기록하지 않았다.

요청은 공개 배경 RPC 1회, 기존 앱과 같은 3600초 서명 2회(1.2초 간격), 각 URL의
HEAD 1회씩으로 종료했다. GET/Range 다운로드와 반복 피드 QA는 0회다. HEAD는
본문 다운로드가 없다는 뜻이지 서버/CDN 처리와 소량 헤더 전송까지 0이라는 뜻은 아니다.

| 항목 | 실제 응답 |
| --- | --- |
| 두 서명 URL | 서로 다름 |
| 두 HEAD 상태 | 모두 HTTP 200 |
| Cache-Control | 모두 `no-cache` |
| CF-Cache-Status | 모두 `MISS` |
| Content-Length | 모두 3,743,173 bytes (약 3.74MB; 본문 미수신) |
| Content-Type | 모두 image/jpeg |
| ETag / Last-Modified | 두 응답에서 동일 |
| Access-Control-Allow-Origin | 모두 `*` |

이 결과는 **스테이징의 익명 공개 배경 객체 1개**에 한정한다. 운영의 로그인 회원
전용 객체, 브라우저 GET/조건부 요청, 과거 누적 전송량의 기여도는 검증하지 않았다.
HEAD MISS를 실제 이미지 전체가 2회 다운로드됐다는 증거로 해석하지 않는다.
`no-cache`를 `no-store`로 바꿔 적거나 브라우저가 어떤 저장도 못 한다고 단정하지 않는다.

URL 변경이 실제로 존재하므로 재사용 여지는 확인됐다. 다만 이 객체의 `no-cache`
응답 때문에 URL 메모리 재사용만으로 전체 미디어 전송 문제가 해결된다고 보고하지
않는다. 다음 우선 검토는 기존 업로드의 Cache-Control 설정 경로와 파일 크기/용도
경계다. 장기 TTL은 삭제·차단 정책과 충돌할 수 있으므로 먼저 변경하지 않는다.
운영 원본 재업로드·일괄 변환·버킷 공개·유료 CDN 도입도 하지 않는다.

진단 스크립트: `/private/tmp/facs-signed-url-headers.mjs`.
이번 단계는 조회·조사 기록만 변경했으며 앱 수정·커밋·운영 배포는 하지 않았다.

## 2026-10-19 후속 — OPS-03D 업로드 캐시·이미지 준비 점검

### 이미 적용된 경로 / 중복 변경하지 않은 부분

- 앱은 upload 옵션에 cacheControl을 지정하지 않지만 설치된 storage-js의
  DEFAULT_FILE_OPTIONS는 `cacheControl: '3600'`이며 업로드에 전달된다.
  옵션 생략을 무캐시 설정 오류로 결론내리거나 같은 값을 명시해 해결했다고 하지 않는다.
- 앞선 익명 signed HEAD의 `no-cache`를 객체의 저장 메타데이터라고 단정할 수 없다.
  버킷/객체 메타데이터와 signed 전달 경로를 구분해야 하며 운영 TTL은 변경하지 않았다.

### 재현한 안전성 결함과 최소 수정

`canvas.getContext('2d')`가 null일 때 기존 optional drawImage는 그리기만 건너뛰고
toBlob 인코딩을 계속했다. 작게 인코딩된 빈 캔버스가 원본 대신 업로드 후보가 될
수 있었다. 로컬 모의 브라우저에서 원본 동일성 테스트가 실제로 실패하는 것을
먼저 확인한 뒤, context가 없으면 즉시 원본 File을 반환하도록 수정했다.

이 수정은 전송량 감소의 증거로 계산하지 않는다. 원본 손실 방지용이며 압축 실패 시
새 차단/오류를 추가하지 않고 기존 원본 업로드를 유지한다. 실제 사용자 이미지나
원격 미디어로 재현하지 않았으며 운영에서 이 결함이 발생했다는 주장도 아니다.

집중 검증은 수정 후 5건 통과:
1. canvas context null → 원본 유지·인코딩하지 않음 (수정 전 실패 확인).
2. 정상 draw → 기존 2048×1536, 더 작은 JPEG, lastModified 보존.
3. 인코딩 결과가 커지거나 예외 → 원본 유지.

## 2026-10-19 후속 — OPS-03E 메타데이터 대조 / 조사 범위 종료

staging guard 통과 후 익명 공개 배경 RPC로 허용된 이미지 1개만 조회했다.
storage-js `info()`가 사용하는 `/object/info/` 읽기 API의 실제 메타데이터는
`cache_control: max-age=3600`, `size: 3743173`, `content_type: image/jpeg`였다.
동일 조회 흐름의 signed HEAD는 200, `no-cache`, `MISS`, Content-Length 3743173.

최초 진단은 info의 snake_case 필드를 camelCase로 읽어 cacheControl을 null로
표시했다. SDK FileObjectV2 타입을 확인해 해석을 수정한 뒤 메타데이터만 읽어
값을 확인했다. HEAD/서명은 재실행하지 않았다. 최초 null은 실제 설정 누락의
증거가 아니며 최종 위 값으로 정정한다. 스크립트는
`/private/tmp/facs-object-cache-info.mjs` (재확인 시 `--metadata-only`).

저장된 캐시 값과 서명 HEAD의 차이는 실제로 확인됐지만, 그 이유가 서버의 HEAD
처리인지 GET에도 적용되는 전달 정책인지는 이번 범위에서 구분하지 않았다.
따라서 `cacheControl: '3600'` 중복 지정, 임의 TTL 연장, 기존 원본 갱신이나
공용 URL 전환을 하지 않는다. 실제 GET·브라우저 전송 기여도는 미확정으로 남긴다.

무료·무다운로드 조사 범위는 여기서 종료한다. 이미 입증·배포한 중복 포스터 요청
제거와 안전성 수정만 릴리스 대상으로 유지하고, 서명 캐시는 효과·권한 경계의
추가 실증 없이 출시 필수 기능으로 확대하지 않는다. 누적 무료 초과 위험은 남는다.
