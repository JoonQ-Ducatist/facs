# 운영 수동 복구본 절차 — 승인된 설계, 실행 대기

상태: 사용자 결정(2026-10-14)에 따라 **복구본 생성·보관·격리 복원은 MVP 출시 이후**. MVP 전 신규 유료 서비스·초과 과금은 0원으로 제한한다. 실제 복구본은 아직 없음. 이 문서는 운영 DB 변경·복원·플랜 변경을 승인하지 않는다.
대상: 공개 도메인에 연결된 Supabase 운영 프로젝트. 프로젝트 이름, CLI 연결, `.env`만으로 운영 대상을 정하지 않는다.

## 중복 확인 (2026-10-14)

- `mvp-release-preflight.md`는 Supabase Free의 자동 백업·PITR 부재와 수동 복구본 필요성을 기록했지만, 생성·보관·복원 절차는 아직 없다.
- 저장소의 `scripts/`와 `supabase/`에는 운영 DB 및 Storage 복구본 생성 스크립트가 없다. 기존 `check:supabase-target:production` 검사를 재사용하고 같은 검사를 새로 만들지 않는다.
- 운영 프로젝트의 과거 사용량 점검, 콘텐츠 완전 삭제 검증, 이미 승인·반영된 정책 문구는 완료 기록을 재사용한다. 아직 미확정인 정식 정책 항목을 이 절차에서 대신 결정하지 않는다.

## 승인된 운영 선택과 미충족 전제

| 항목 | 승인된 선택 | 현재 상태 |
| --- | --- | --- |
| 보관 위치 | 로컬 **암호화된** 작업본. 별도 비공개 Backblaze B2 버킷은 **0원 지출을 확실히 통제할 수 있을 때만** 추가하고, 평문과 복호화 개인키는 올리지 않음 | B2 계정·버킷 미생성. 과금 가능성이 남으면 MVP 후로 연기 |
| 암호화·키 | 파일 단위 공개키 암호화(`age` 후보). `Joon (Manager)`이 개인키를 비밀번호 관리자에 보관하고 별도 오프라인 복구 사본 관리 | 도구·키 미준비. 키를 Git·채팅·로그·B2에 기록하지 않음 |

| 비용 원칙 | MVP 공개 후 사용자가 증가하기 전까지 신규 유료 서비스·초과 과금 없음. Supabase Pro 전환하지 않음 | 기존 플랜 유지. 무료 할당량은 무과금 보증이 아님 |

2026-10-14 `npm run check:supabase-target:production`은 운영 ref `rrcntobfmxlwbbjtlbge`와 현재 CLI 연결 ref `zvaheyfumpmzrolsbtrf`의 불일치로 중단됐다. 이 상태에서 운영 덤프를 실행하거나 CLI 연결을 임의 변경하지 않는다.

## 복구 범위

| 영역 | 필요한 복구본 또는 기록 | 확인 기준 |
| --- | --- | --- |
| Postgres | 앱 테이블 데이터, 스키마·권한, Auth 사용자·ID 연결, 마이그레이션 이력의 복원 가능 범위 | 별도 프로젝트에서 로그인 계정과 게시물·평가·신고 관계를 복구할 수 있음 |
| Storage | `facs-media`의 실제 객체 바이트와 bucket·객체 메타데이터 | DB의 미디어 참조와 복원 객체의 개수·크기·해시가 일치함 |
| Dashboard 설정 | Google OAuth, Resend SMTP, URL 허용 목록, 키·비밀값, Storage 정책 등 DB 덤프 밖 설정의 재구성 목록 | 비밀값 자체를 문서·Git·백업 매니페스트에 남기지 않고 복구 담당자가 재설정 가능함 |
| 앱·배포 | Git 커밋, Vercel 운영 프로젝트 ID와 도메인·환경변수 키 목록 | 복원 대상과 배포 소스를 혼동하지 않고 앱을 다시 연결할 수 있음 |

Supabase CLI의 기본 `db dump`는 데이터가 없고 `auth`·`storage` 등 관리 스키마를 제외한다. 따라서 기본 덤프 파일 하나를 전체 복구본이라고 판정하지 않는다. DB 백업에는 Storage 객체 파일도 포함되지 않는다.

## 실행 순서 (운영 데이터 추출 전 전제 충족 필요)

1. `factsmack.com`이 연결된 Vercel 프로젝트의 Production `VITE_SUPABASE_URL` 호스트와 Supabase Dashboard 프로젝트 ref를 **그 실행일에** 읽기 전용으로 대조한다. DB 명령 전 `npm run check:supabase-target:production`을 실행한다. 셋 중 하나라도 불일치하면 중단한다.
2. 암호화 공개키·개인키의 분리 보관과 실행 호스트의 암호화된 로컬 저장소를 먼저 준비한다. 별도 비공개 B2 버킷·버킷 한정 키는 과금 위험이 **0원 조건과 양립함을 확인한 경우에만** 준비한다. 확인 전에는 B2 업로드를 하지 않는다. 비밀값은 저장소나 이 문서에 넣지 않는다.
3. Supabase 공식 복구 절차를 기준으로 역할·스키마·데이터의 **실제 복원 가능 범위**를 격리 환경에서 먼저 검증한다. 기본 `db dump` 하나로 Auth 사용자·Storage 메타데이터까지 확보됐다고 가정하지 않는다. 운영 추출 시에는 같은 실행의 DB 덤프와 Storage 인벤토리 시각을 매니페스트에 기록하고, 복사 중 변경이 생기면 불일치로 표시한다.
4. Storage는 매일 전체 객체 목록과 이전 성공 매니페스트를 비교하여 새로 생기거나 변경된 객체 바이트만 원본에서 내려받는다. 경로·크기·갱신시각만으로 동일성을 단정하지 않고, 다운로드한 바이트의 해시를 기록한다. 새 매니페스트가 참조하는 기존 암호화 객체는 업로드 날짜가 7일을 넘었어도 지우지 않는다.
5. 평문 임시 파일은 권한 제한된 임시 위치에서 즉시 암호화하고, 성공·실패 양쪽에서 정리한다. 암호화된 DB·객체와 매니페스트를 로컬에 보관하며 크기·해시를 확인한다. B2 비용 조건이 충족된 뒤에만 외부 사본을 추가한다. 매니페스트에는 시각, 확인된 프로젝트 ref, 앱 커밋, DB/객체 건수와 총크기, 해시, 도구 버전, 실패 건수만 기록하고 토큰·연결 문자열·개인정보 원문은 넣지 않는다.
6. **새 복구 시점이 온전히 생성·검증된 뒤에만** 7일을 넘긴 이전 시점과 어느 보유 시점에서도 참조하지 않는 암호화 객체를 정리한다. 실패한 실행은 기존 복구본을 만료시키지 않는다. B2를 사용할 때에는 기본 파일 버전 보유도 별도로 검증하며, 단순 7일 업로드 수명주기 규칙으로 현재 참조 중인 객체를 삭제하지 않는다.
7. 복원 연습은 운영 프로젝트가 아닌 격리된 대상으로 한다. 암호화된 로컬 사본(외부 사본이 활성화됐다면 해당 사본도)을 개인키로 복호화한 뒤 DB 구조·데이터, Auth 관계, 실제 Storage 파일과 외부 설정을 복원하고 로그인·미디어 읽기·평가·삭제의 최소 흐름을 확인한다. 실제 운영 복원은 별도 장애 판단과 승인 후 수행한다.
8. 복원본의 정보가 운영에서 이미 삭제된 콘텐츠를 되살릴 수 있으므로, 복원 시점 이후의 삭제·정정 요청을 대조하고 공개 전 재처리한다. 이 재처리가 검증되기 전에는 복원본을 공개 서비스에 연결하지 않는다. 연습 후 격리 데이터는 별도 승인된 정리 절차로 처리한다.

## 완료 판정

- 운영 대상 일치 증거, 암호화된 DB·Storage 복구본, 매니페스트가 있다.
- 격리 환경 복원에서 계정·콘텐츠·미디어의 연결과 핵심 동작이 확인됐다.
- 보유·파기 기간과 삭제 요청 재처리 절차가 정책 검토 결과와 일치한다.
- 운영 복원 책임자와 키 접근자가 지정됐다.

현재는 위 조건이 충족되지 않았다. 암호화 도구·키, 실행 주체가 없고 CLI도 스테이징에 연결되어 있다. 이 호스트에서 `pg_dump`와 `psql`도 확인되지 않았다. B2 계정·버킷도 없으며, B2의 첫 10GB 무료 용량과 데이터 사용 제한/알림만으로 **절대 0원 과금을 보증하지는 않는다**. 과금 위험을 해소하기 전까지 외부 업로드를 활성화하지 않는다. 로컬 단일 사본만으로는 기기 고장·분실에 대비한 복구 완료로 판정하지 않는다. 운영 데이터 추출과 격리 복원은 아직 시작하지 않는다.
