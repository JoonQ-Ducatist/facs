## 동적 업무 배분

1. 마스터는 새 요청마다 `list_threads`로 실제 존재하는 작업을 확인한다.
2. 아래 초기 등록부는 힌트다. ID의 존재, 현재 제목, 프로젝트, 담당 범위와
   실행 상태를 확인한다. 삭제/보관된 작업에는 보내지 않는다.
3. 새 작업은 프로젝트와 사용자 지정 역할, 필요한 경우 최근 대화를 읽고
   배분 후보에 포함한다. 제목이 비슷하다는 이유만으로 선택하지 않는다.
4. 동일 요청의 진행 작업이 있으면 그 작업에 후속 지시한다. 중복 실행하지 않는다.
5. 사용자가 새 대화방 생성을 요청한 경우에만 새 사용자 대화방을 만든다.
   적합한 작업이 없으면 PM이 처리하거나 한 번의 필요한 역할 질문을 한다.
6. `send_message_to_thread`로 명세를 전달하고 `wait_threads`로 결과를 회수한다.
   실행 중인 작업에 충돌하는 수정 지시를 덧붙이지 않는다.
7. 큰 작업은 독립된 디자인/리뷰/검증 준비를 병렬 배분할 수 있다.
   같은 파일은 한 구현 담당만 수정한다.

## 전달 계약

각 요청은 `FACS-YYYYMMDD-NNN` 등의 고유 ID를 가지며 아래 내용을 포함한다.

- 목적, 요청 원문 요약, 완료 기준, 제외 범위
- 담당 역할, 실제 저장소 절대 경로, 기준 커밋/브랜치, 기존 dirty 상태
- 수정 소유 파일, 의존 작업, 테스트 모드(mock/staging/production)
- 반환할 증거와 보고 대상 PM ID

담당자는 완료/진행/차단 상태, 변경 파일, 테스트 결과, 미검증 항목,
커밋/PR/미리보기 주소를 반환한다. 결과를 PM에 한 번 전달하고 재배분하지 않는다.
PM은 문제를 재현하거나 증거를 확인한 뒤 수정 담당에게 반환한다.
QA의 PASS는 제품 승인 또는 보안 전체 통과를 뜻하지 않는다.

## 검증 및 출시

### 필수 승인 게이트

코드·UI 동작을 변경하는 모든 과제는 아래 순서를 지킨다.

1. PM이 과제 ID, 범위, 완료 기준과 수정 소유자를 확정한다.
2. 구현 담당은 최신 `main`에서 과제 브랜치를 만들고 그 브랜치에서만 수정한다.
3. 구현 담당은 로컬 테스트·빌드를 통과시킨 뒤 브랜치에 커밋·푸시한다.
4. `main` 대상 Draft PR을 만들고 CI 결과와 Vercel Preview URL을 고정한다.
5. Antigravity는 해당 커밋과 Preview URL을 브라우저 QA하고 증거를 반환한다.
6. PM은 CI·QA 결과와 미검증 범위를 사용자에게 보고한다.
7. 사용자와 Antigravity가 모두 승인한 뒤에만 PR을 `main`에 병합한다.
8. 운영 배포의 짧은 smoke test 후 과제를 완료 처리하고 다음 순번을 시작한다.

- `main`에서 직접 구현하거나 승인 전에 병합·운영 배포하지 않는다.
- Antigravity 결과가 `BLOCKED`, `INCOMPLETE`, `STALE_SOURCE`이면 승인으로 보지 않는다.
- QA 후 코드가 바뀌면 커밋과 Preview가 달라졌으므로 CI와 영향 범위 QA를 다시 실행한다.
- 사용자의 승인 문구는 반드시 `★ PM ★`에 기록한다. 다른 공간의 의견은 최종 승인으로 대체하지 않는다.
- 문서만 바꾸는 과제도 브랜치와 사용자 검토를 거치되, 실행 화면에 영향이 없으면 Preview·Antigravity QA는 PM이 제외 사유를 기록할 수 있다.
- 운영 장애의 긴급 수정만 사용자의 명시적 승인 후 `main` 직접 반영을 허용하며, 사후 테스트와 기록을 남긴다.
- 승인 또는 병합 전에는 다음 순번의 구현을 시작하지 않는다. 다음 과제의 조사·QA 시나리오 준비만 병렬로 할 수 있다.

### 브랜치와 검증 기준

- 브랜치명: `feat/facs-<task>-<summary>`, `fix/facs-<task>-<summary>`, `chore/facs-<task>-<summary>`.
- 명세 -> 구현/QA 시나리오 준비 -> 브랜치 커밋 고정 -> Draft PR ->
  CI/독립 리뷰/브라우저 QA -> 수정 -> 영향 범위 재검증 -> 사용자 승인 -> main 병합.
- UI 미리보기와 실제 인증/DB 검증을 분리한다. 모의 로그인은 인증 통과가 아니다.
- 결과 정책은 result-contract.md를 따르며 예시의 20표 기준으로 덮어쓰지 않는다.
- 브라우저 QA는 ko/en, 모바일/데스크톱, 실패/빈 상태, 키보드 접근성을 포함한다.
- Chrome 화면 축소를 Safari/실기기 테스트라고 기록하지 않는다.
- Antigravity는 운영 데이터 변경, 결제, 배포, 코드 수정, 정책 변경을 수행하지 않는다.
- 테스트/빌드는 PR 기준으로 실행한다. QA 보고서는 정확한 커밋과 URL에 귀속한다.
- 기능별 브랜치와 `main` PR 흐름은 선택 사항이 아니라 필수다. 자동 병합은 사용하지 않는다.
- QA 명령과 설치 상태는 `memory-bank/antigravity-qa.md`를 참고한다.
