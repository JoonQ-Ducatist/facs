# FACt.Smack 서비스 설계 규칙 (Memory Bank)

> 이 문서는 FACt.Smack의 제품 의도, 서비스 원칙, 기술 경계를 기록하는 기준 문서다.
> 기능·데이터 모델·API·UI를 변경하기 전에 확인하고, 합의된 결정이 생기면 이 문서를 함께 갱신한다. 단, 제품의 최상위 판단 기준은 [Product Philosophy](./product-philosophy.md)이며, 수익화·Growth·일정 판단은 [90-day Cash Loop Plan](./90-day-cash-loop-plan.md)과 [Monetization](./monetization.md)을 따른다. 본 문서와 충돌할 경우 해당 문서를 우선한다.

## 1. 서비스 정의

### 브랜드 표기

- 서비스명과 화면 워드마크는 **FACt.Smack**로 표기한다. 패키지·저장 키·도메인·저장소 같은 기술 식별자는 소문자 **facs**를 사용한다.
- 공식 서비스명은 **FACt.Smack**이며, 제품·문서·검색·인증·공유·운영 표기에서 이 이름을 사용한다. 제품 화면에서의 짧은 별칭은 영문 대문자 **FACS**로만 표기한다.
- UI 타이포그래피는 콘텐츠 중심의 Neutral Sans Serif를 기본으로 하며, 한글은 **Pretendard Variable**, 영어·라틴 문자·숫자는 **Inter Variable**을 사용한다. 강조를 위한 별도 세리프 서체는 사용하지 않는다.
- 사용자 콘텐츠를 묶어 소개하는 화면·기능의 제품 용어는 **Look Book**으로 통일한다. 한국어 문장에서는 자연스러운 맥락에 한해 **룩**을 병행한다.
- 브랜드 사용 시 성적·오컬트 연상을 강화하는 문구나 그래픽은 피하고, 다양한 관점에서 나를 확인하는 서비스 경험을 우선한다.

#### FACt.Smack 핵심 브랜드 언어

- 브랜드 구조 **FACT → FACTSMACK → FACS → FACTS/FAX**는 장기 브랜드 자산으로 유지한다. `FACS`는 `FACTS`의 음감과 `FAX`의 정보 송수신 의미를 연결하지만, 이 연결은 화면 표기가 아닌 브랜드 해석에 한정한다.
- 공식 브랜드명은 **FACt.Smack**, 제품 UI의 짧은 표기는 **FACS**다. 헤더·로고·버튼·알림·기능명·온보딩·결과·공유·빈 상태 등 모든 사용자 대면 디자인 요소에서는 한글 **‘팩스’**를 사용하지 않는다.
- 비주얼 워드마크는 **FACS**를 우선 강조하고, 필요할 때만 보조 정보로 **FACT.SMACK** 또는 **FACt.Smack**을 사용한다. `FAC`와 `S`는 색상·굵기 등으로 함께 강조할 수 있다.
- **‘팩스’**는 대외 광고·캠페인·마케팅 실험에서만 선택적으로 쓸 수 있는 한국어 언어유희다. 제품 UI나 영구 브랜드 자산에는 포함하지 않으며, 사용 전에는 별도 카피 승인을 받는다.
- 향후 로고, UI/UX, 알림, 기능명, 브랜드 스토리 설계에서는 위 표기 경계를 우선한다. 다음 브랜드 작업은 FACS 워드마크의 실제 헤더 인지·가독성을 검증하는 것이다.

**FACt.Smack**은 사용자가 사진과 상황별 질문을 올리고, 다른 사용자의 빠른 평가를 통해 첫인상에 대한 정량적 피드백을 받는 서비스다. 기본 평가는 YES/NO이며, `PERCEIVED_AGE`만 숫자 나이 평가를 사용한다.

- 핵심 가치: 주관적인 첫인상을 이해하기 쉬운 데이터와 피드백으로 전환한다.
- 주요 상황: 데일리 스타일, **몇 살로 보여?**, 소개팅/데이트, 운동/피트니스, 출근/커리어, SNS 프로필. 여행은 초기 MVP 범위에서 제외한다.
- 현재 단계: 브라우저 내 동작하는 SPA 프로토타입.
- 목표 단계: 인증된 사용자가 사진을 안전하게 업로드하고, 실제 투표와 분석 결과를 받을 수 있는 웹 서비스.

## 2. 사용자와 핵심 흐름

### 역할

- **업로더**: 사진, 카테고리, 질문을 등록하고 결과를 확인한다.
- **평가자**: 피드를 탐색하며 각 카드에 한 번씩 YES 또는 NO로 반응한다.
- **운영자**: 신고·콘텐츠 검토·안전 정책을 관리한다.
- **관리자**: 역할·서비스 설정·카테고리·이미지 처리 정책을 관리하며, 모든 변경은 감사 로그로 남긴다.
  - 회원관리 범위: 계정 검색·상태 조회, 역할 부여·회수, 이용 제한·해제, 탈퇴 처리 요청 관리. 개인정보는 업무에 필요한 최소 정보만 열람한다.
  - 평가자 식별 정보는 일반 사용자·업로더에게 공개하지 않으며, 관리자만 부정행위·분쟁·법적 요청 목적의 최소 범위에서 감사 로그와 함께 열람한다.

### 핵심 여정

1. 업로더가 사진과 질문, 카테고리를 등록한다.
2. 서비스는 공개 전 정책 검토 상태를 관리한다.
3. 평가자가 피드에서 카드를 보고 카테고리의 Evaluation Type에 맞춰 응답한다.
4. 업로더는 득표 수, 긍정률, 카테고리별 통계를 확인한다.
5. 기준을 충족한 콘텐츠는 랭킹에 노출될 수 있다.

## 3. 제품 규칙

- 질문은 하나의 첫인상 판단에 집중한다. 기본 카테고리는 `BINARY` YES/NO 중 하나만 선택하고, `PERCEIVED_AGE`는 `NUMERIC_AGE` 정수 나이(18~99)를 빠르게 선택한다. Category와 Evaluation Type은 DB·API·UI에서 분리한다.
- `PERCEIVED_AGE`의 표시명은 **몇 살로 보여?**, 글로벌 표기는 **How Old Do I Look?**, 내부 ID는 **PERCEIVED_AGE**다. 정렬은 `몇 살로 보여? → 오늘의 룩 → 데이트 → 운동 → 출근 → SNS 프로필`로 고정한다.
- `PERCEIVED_AGE` 업로더는 평가 최소·최대 나이를 18~99세 범위에서 지정한다. 평가자는 지정 범위의 슬라이더로 나이를 고르고, ± 제어로 한 살씩 미세 조정한 뒤 제출한다.
- 실제 나이는 선택 입력이며, 평가자·피드·프로필·공유 카드에 노출하지 않는다. 업로더 본인에게만 권한 있는 결과 화면에서 평균 예상 나이와 비교할 수 있다.
- `PERCEIVED_AGE` 결과는 AI 측정값 또는 객관적 사실로 말하지 않고 **참여자의 주관적인 첫인상**으로만 안내한다. 표본이 충분하지 않으면 확정 수치처럼 표현하지 않는다.
- 업로드 질문 입력 영역은 사용자의 평가 니즈를 묻는 언어로 표현한다. 각 카테고리마다 추천 질문 4개를 제공하며, 사용자가 추천 문장을 선택하면 입력값에 즉시 반영하고 `지우고 다시 작성`으로 빈 입력 상태에서 직접 작성할 수 있게 한다. 프로토타입은 선택 미디어 수·유형을 맥락으로 문구를 조정하며, 실제 이미지 내용 분석 기반 추천은 서버 측 안전한 AI 분석이 준비된 뒤 도입한다.
- PC 환경의 업로드 영역은 로컬 디바이스 파일 선택을 기본으로 유지하고, 같은 영역에 파일을 끌어놓는 Drag & Drop도 지원한다. 모바일에서는 탭 기반 파일 선택을 우선한다.
- 하단 주요 메뉴에서 선택된 Feed·Upload·Ranking·Profile은 각 메뉴 고유의 밝은 포인트 색으로 구분한다. 콘텐츠 자체의 카테고리 색과 혼동되지 않도록 메뉴 색은 탐색 상태에만 사용한다.
- 투표 결과는 충분한 표본이 쌓이기 전까지 확정적 평가처럼 표현하지 않는다.
- 랭킹은 단순 긍정률뿐 아니라 최소 투표 수와 신뢰도 기준을 함께 고려한다.
- 사용자는 본인이 올린 콘텐츠를 삭제할 수 있어야 하며, 삭제 시 원본 이미지와 연결된 공개 노출을 함께 제거한다.
- 카테고리별 색상과 문구는 일관되게 유지한다.
- 한국어·영어를 포함한 모든 서비스 문구는 PC·모바일에서 어색한 단어 쪼개짐이 없어야 한다. 핵심 질문·설명은 관련 문장의 균형 잡힘을 우선하고, 짧은 제어·수치는 한 줄을 유지하며, 폭이 좁은 화면에서는 줄바꿈을 강요하지 말고 컨트롤의 행·열을 재배치한다. 새 화면은 `ko`/`en` 단어 길이와 320px부터 PC까지의 대표 폭을 검증해야 한다.
- 피드 카드의 핵심 질문처럼 브랜드 경험상 줄 수가 고정돼야 하는 문구는 번역본에도 같은 의미 단위의 명시적 줄바꿈을 제공한다. 제목 크기는 뷰포트가 아닌 카드 컨테이너 폭을 기준으로 조절해 PC·모바일·모달에서 같은 콘텐츠가 임의로 한 줄과 두 줄 사이를 오가지 않게 한다.
- 개발·QA는 한국어와 영어를 항상 함께 고려한다. 다만 로컬 라이브의 기본 언어는 한국어이며, 영어 로컬 라이브는 사용자가 명시적으로 요청한 경우에만 연다.
- 로컬 라이브와 `preview` 쿼리가 붙은 검토 URL은 저장된 로그인 세션과 관계없이 항상 스플래시부터 시작한다. 검토자는 스플래시 상단의 뱀 로고 또는 `FACt.Smack` 워드마크를 눌러 인증 없이 피드 점검으로 진입한다.
- 프로토타입과 현재 배포 서비스의 언어 기본값은 환경·브라우저 언어와 무관하게 한국어로 고정한다. 사용자는 헤더의 언어 전환으로 한국어·영어를 직접 바꿀 수 있고, 이 선택은 `locale=ko` 또는 `locale=en` URL 값으로 명시해 새로고침과 배포 환경에서도 유지한다. IP·국가·브라우저 언어 기반 자동 전환은 개인정보 고지·서버 측 정책·번역 검수가 완료되기 전에는 사용하지 않는다. 중국어는 번역 카탈로그·검수 완료 전 자동 전환 대상에 포함하지 않는다.
- 목업 피드는 카테고리별 서로 다른 사용자 카드 약 5개를 유지하고, 동일 사진은 다른 카드에 재사용하지 않는다. 카드 미디어 수는 서비스 전체에서 1·2·3·4·5장을 모두 검증할 수 있게 배정하며, 다인물 합성·콜라주·잘린 사진은 사용하지 않는다.
- iOS Safari 등의 세션 복귀에서도 상단 헤더와 본문 시작점은 항상 복원돼야 한다. 모바일은 전체 폭, PC는 좌측 탐색·중앙 520px 피드·우측 280~300px 추천 영역을 기본으로 하며, 어느 폭에서도 카드·카테고리·텍스트가 컨테이너 밖으로 넘치지 않아야 한다.
- 스마트폰은 세로 모드만 제품 레이아웃으로 제공한다. 웹은 OS 회전을 직접 잠글 수 없으므로, 600px 미만 가로 회전에서는 앱 콘텐츠 대신 세로 모드 복귀 안내만 표시한다. 태블릿·PC는 해당 제한 대상이 아니다.
- 2026-09-04 기준 주요 SNS의 선명한 포인트 컬러를 참고해 카테고리 색을 구분한다. `몇 살로 보여? #FF0050`(short-form 계열 핑크), `오늘의 룩 #FF6B35`(코랄 오렌지), `데이트 #A855F7`(바이올렛), `운동 #22C55E`(그린), `출근 #2563EB`(로열 블루), `SNS 프로필 #F59E0B`(앰버). 이 토큰은 탭·피드 카드·투표·랭킹·업로드의 해당 카테고리 강조에 공통 적용한다. YES는 카테고리 색을, NO는 구별 가능한 다크 레드 `#B42318`을 사용한다.
- 회원 상태 변경(활성, 제한, 정지, 탈퇴)은 관리자만 수행하며, 대상·사유·변경 전후 상태·처리 시각을 감사 로그에 남긴다.
- 카테고리의 생성·수정·숨김·삭제·정렬은 관리자만 수행한다. 공개 중인 카테고리는 삭제 대신 숨김 또는 보관을 우선한다.
- 카테고리 순서는 관리자가 명시적으로 관리하며, 사용자 피드·업로드 선택지·랭킹 필터에 같은 순서로 반영한다.
- 업로드 이미지와 동영상은 모바일 네트워크와 화면 크기에 맞게 서버에서 최적화된 파생본을 제공한다. 원본 보관·삭제 정책은 별도로 적용한다.
- 업로드 미디어는 날짜(UTC), 미디어 유형, 게시물 ID, 무작위 자산 ID를 조합한 객체 스토리지 키로 분리 저장한다. 예: `uploads/2026/08/25/image/{postId}/{assetId}/original.ext`. 원본과 공개용 파생본은 별도 경로로 저장하고, 경로에는 사용자 ID·이메일·핸들 등 식별 정보를 넣지 않는다.
- 초기 동영상 업로드는 길이 10초 이하의 짧은 동영상만 허용한다. 길이는 클라이언트 미리 검증과 서버 검증을 모두 적용하며, 실제 공개 전 형식·용량·안전 검사와 검토 절차를 거친다.
- 업로더는 선택한 미디어의 표시 순서를 변경할 수 있으며, 첫 번째 미디어를 게시물의 대표 미디어로 사용한다. 이 순서는 서버에 영구 저장하고 관리자 조회·감사 대상에 포함한다.
- 비로그인 방문자는 전체 피드 대신 스플래시 화면에서 공개 동의·게시 상태를 충족한 인기 콘텐츠 5~10개의 무작위 미리보기만 볼 수 있다. 해당 화면은 한국어와 영어의 가입 유도 문구 및 회원가입·로그인 진입점을 제공한다.
- 비로그인 미리보기의 인기 기준, 노출 수, 노출 가능 상태, 문구는 관리자 설정으로 관리하고, 비공개·검토 중·삭제·차단 콘텐츠는 절대 노출하지 않는다.
- 회원가입·로그인은 Apple, Google, Kakao 및 이메일 방식을 제공한다. 하나의 사용자 계정에 여러 인증 수단을 안전하게 연결할 수 있어야 하며, 인증 제공자별 공식 버튼·브랜딩을 사용한다.
- 로그인한 회원은 모든 전체 공개 게시물을 열람하고 YES/NO 투표할 수 있다.
- 게시물·댓글·공개 프로필에는 실명 대신 사용자가 설정한 `@핸들`만 표시한다. 실명·이메일·인증 제공자 정보는 일반 사용자에게 공개하지 않는다.
- 프로필 사진 옆의 설정 버튼은 **개인 계정 설정** 진입점이다. 여기에서 프로필 사진·`@핸들`, 연결된 로그인 수단, 알림, 기본 공개 범위·댓글 기본값, 차단 목록, 탈퇴·데이터 요청을 관리한다. 게시물별 공개 범위·댓글 허용은 게시물 작성·수정 화면에서 최종 선택하며, 관리자·운영 기능은 이 버튼에 포함하지 않는다.
- 초기 사용자 모집 기간에는 모든 로그인 회원이 별도 승인 없이 사진을 업로드할 수 있다. 이후 서비스 규모·품질 지표가 기준에 도달하면, 투표 또는 댓글 활동 기준을 충족한 회원만 업로드하도록 전환할 수 있다.
- 사용자는 본인이 직접 촬영했거나 공개·사용 권한을 보유한 사진만 업로드할 수 있다. 업로드 시 권리 보유 확인 동의를 받고, 동의 시각·버전은 감사 기록으로 보관한다.
- 초기 서비스에는 연령 제한을 적용하지 않는다. 운영 중 카드 검토·신고·안전 지표를 근거로 연령 제한 필요성을 재검토하고, 전환 전에 사용자에게 알림과 결정을 요청한다.
- 업로드 자격 전환 규칙은 초기에는 비활성으로 두며, 활성화 전에 사용자 수·활동·신고율 등 운영 지표를 검토해 사용자에게 전환 시점과 기준을 알리고 승인받는다. 기준값과 댓글 도입 여부는 별도 결정이 필요하다.
- 업로더는 게시물마다 `전체 공개` 또는 `팔로워 공개` 범위를 선택한다. 팔로워 공개 게시물은 업로더와 권한 있는 팔로워만 열람·투표할 수 있으며, 비로그인 미리보기·랭킹·검색 노출에서 제외한다.
- 업로더는 게시물별 댓글 허용 여부를 선택한다. 댓글이 허용된 게시물은 원댓글과 원댓글당 한 단계의 대댓글만 지원하며, 대댓글에는 다시 답글을 달 수 없다.
- 게시물을 열람할 권한이 있는 로그인 회원은 댓글 허용 게시물에 댓글·한 단계 대댓글을 작성할 수 있다. 게시물 공개 범위, 댓글 허용 여부, 차단·계정 상태를 서버에서 모두 확인한다.
- 댓글에는 신고 기능을 제공한다. 신고가 접수되면 운영자 검토 대기 상태가 되며, 운영자는 검토 후 댓글을 숨김 처리할 수 있다.
- 댓글과 게시물의 신고 사유는 `스팸·광고`, `혐오·차별`, `괴롭힘·욕설`, `성적 콘텐츠`, `개인정보 노출`, `타인 비방`, `사회 통념 위반`, `기타`로 통일한다.
- 작성자는 자신의 댓글을 즉시 `삭제`할 수 있다. 사용자 화면에서는 삭제로 표시하되, 기술적으로는 감사·신고 처리에 필요한 메타데이터를 유지하는 숨김(소프트 삭제)으로 처리한다.
- 관리자는 신고 검토 후 댓글을 삭제 조치할 수 있다. 모든 숨김·삭제 조치는 주체, 사유, 시각, 이전·이후 상태를 감사 로그에 남긴다.
- 운영자 숨김 또는 관리자 삭제 조치에 대한 작성자의 이의 제기 기능은 제공하지 않는다.
- 모든 게시물·댓글의 `삭제`는 사용자 화면에서만 삭제로 표현하며, 기술적으로는 소프트 삭제로 처리한다. 소프트 삭제된 콘텐츠와 메타데이터는 일반 사용자·운영자에게 노출하지 않고, 별도 권한을 가진 관리자만 admin 화면에서 열람할 수 있다.
- 댓글은 기본 화면에서 최신·관련 댓글 2~3개만 스크롤 가능한 요약 영역으로 보여 주고, `전체 보기`를 선택하면 댓글 영역을 확장해 전체 목록을 제공한다. 서비스는 특정 SNS의 화면을 복제하지 않고 익숙한 모바일 상호작용 원칙만 참고한다.
- 게시물은 사진을 최대 5장까지 등록할 수 있다. 여러 사진은 좌·우 스와이프로 탐색하고, 현재 사진 위치와 전체 장수를 작게 표시한다.
- 팔로우는 승인 없는 단방향 관계로 즉시 성립한다. 언팔로우·차단·계정 상태 변경 시 팔로워 공개 콘텐츠의 접근 권한은 즉시 다시 계산한다.
- 위치 기반 촬영 정보, 모바일 햅틱, 언어·지역 가격, Boost 우선 노출, Bitcoin 결제와 Tournament 5:5 규칙은 [글로벌 운영·사실성·결제 규칙](./global-service-rules.md)을 따른다.
- 사용자가 다른 사용자를 차단하면 양쪽 모두 서로의 게시물·댓글·프로필·팔로우 관계를 볼 수 없고 상호작용할 수 없다. 기존 팔로우 관계는 해제하며, 차단 기록은 일반 사용자에게 노출하지 않고 권한 있는 관리자만 감사 목적으로 열람한다.
- 초기 관리자 권한은 사용자님의 Google 인증 계정 하나에만 부여한다. 이후 최고 관리자는 하위 관리자를 추가·비활성화할 수 있으며, 모든 권한 변경은 감사 로그에 남긴다.
- 관리자 역할은 `Super Admin`, `콘텐츠 검토 관리자`, `회원 관리 관리자`, `설정 관리 관리자`로 분리한다. Super Admin은 모든 권한을 가지며 다른 Super Admin과 하위 관리자를 추가·비활성화·권한 변경할 수 있다. 하위 관리자는 자신에게 부여된 역할 범위를 넘는 작업과 관리자 권한 관리를 할 수 없다.
- 관리자 기능은 일반 사용자 서비스와 분리된 웹 도메인에서 제공하며, 관리자 개발 소스는 별도 디렉터리와 별도 Git 저장소로 관리한다. 실제 도메인·저장소·계정 식별값은 비밀 관리 설정으로만 관리하고 저장소에 기록하지 않는다.
- 현재 프로토타입의 localStorage 데이터는 실제 서비스 데이터로 간주하지 않는다.

## 4. 안전·프라이버시 원칙

- 사진은 민감한 개인 데이터로 취급한다. 업로드·열람·삭제 권한을 명확히 분리한다.
- 실명, 연락처, 위치, 타인의 개인정보가 포함된 콘텐츠는 제한하거나 신고·검토 흐름을 둔다.
- 외모 비하, 차별, 성적 대상화, 괴롭힘을 유도하는 질문과 댓글은 허용하지 않는다.
- 초기 서비스에는 가입·업로드의 연령 제한을 두지 않는다. 미성년자로 의심되는 사진 관련 신고·검토 지표를 운영하며, 연령 제한 또는 추가 보호 정책이 필요하다고 판단되는 시점에 사용자에게 알리고 별도 결정을 받는다.
- 원본 이미지 URL, 인증 토큰, 개인 식별 정보는 클라이언트 코드나 Git 저장소에 기록하지 않는다.
- 분석 결과는 참고용 피드백이며 사람의 가치·능력에 대한 단정으로 표현하지 않는다.

## 5. 기술 설계 원칙

- **Supabase를 실서비스 백엔드 기준 플랫폼으로 사용한다.** Supabase Postgres는 영구 데이터, Supabase Auth는 계정·세션, Supabase Storage는 비공개 원본·공개 파생 미디어, Edge Functions는 권한 있는 쓰기·운영 작업을 담당한다.
- 프론트엔드, API, 인증, DB, 이미지 저장소를 분리한다.
- 클라이언트는 직접 DB 또는 비밀 키에 접근하지 않는다.
- 브라우저에는 Supabase anon key만 사용하고, 테이블·Storage 접근은 Row Level Security(RLS) 정책으로 최소 권한을 강제한다. service role key는 Edge Functions 또는 신뢰 가능한 서버 환경에서만 사용한다.
- 모든 변경 API는 인증·인가·입력 검증·감사 로그를 기본으로 한다.
- 이미지 업로드는 크기·형식 검사, 악성 파일 검사, 접근 제어가 가능한 저장소를 사용한다.
- 이미지·동영상의 무거운 검사·변환은 브라우저나 공개 Edge Function에 맡기지 않고, Supabase Storage와 연동한 별도 비동기 워커에서 수행한다.
- 투표는 사용자·카드 단위 중복 방지와 비정상 트래픽 방지를 갖춘다.
- API 응답은 버전 관리하고, 오류 형식과 권한 오류를 일관되게 제공한다.
- 새로운 외부 서비스·SDK·비밀값을 추가하기 전에는 이 문서에 목적과 데이터 흐름을 기록한다.

## 6. 권장 도메인 모델

- **User**: 계정, 프로필, 역할, 상태
- **Post/Card**: 최대 이미지 5개와 동영상 1개(동영상 최대 10초)의 업로드 미디어, 작성자, 카테고리, 질문, 공개 범위, 댓글 허용 여부, 공개·검토 상태
- **Media**: postId, 유형(image/video), 원본·파생본 객체 키, MIME type, 크기·해상도·재생 시간, 처리 상태, 삭제 상태, 생성 시각
- **Vote**: 카드, 평가자, 선택값, 생성 시각
- **Comment**: 게시물, 작성자, 본문, 부모 댓글(선택), 깊이, 상태, 생성·수정 시각
- **Comment 상태**: `visible → reported → hidden_by_author/hidden_by_operator → soft_deleted_by_admin`. 신고 자체는 검토 상태이며, 관리자 삭제도 소프트 삭제로 처리한다.
- **Aggregate**: 총 투표 수, YES 수, NO 수, 긍정률, 신뢰도
- **Report/ModerationCase**: 신고 대상, 사유, 처리 상태, 운영 기록

## 7. 현재 구현과의 차이

현재 저장소는 HTML/CSS/Vanilla JavaScript 기반의 단일 페이지 프로토타입이며, 카드·투표·업로드 결과가 브라우저 localStorage에만 저장된다.

실서비스 전환 시 우선순위는 다음과 같다.

1. 사용자 인증과 계정 모델
2. 안전한 이미지 업로드·저장·삭제
3. Post와 Vote API 및 영구 데이터베이스
4. 중복 방지·집계·랭킹 로직
5. 신고·검토·차단 정책과 운영 도구
6. 개인정보 처리와 서비스 약관

## 8. 작업 규칙

- 기능을 구현하거나 수정하기 전, 이 문서에 정의된 서비스 목적·안전 원칙·기술 경계를 확인한다.
- 새 결정은 `결정 기록`에 날짜와 이유를 짧게 추가한다.
- 기존 원칙을 바꾸는 작업은 코드 변경과 같은 커밋에서 이 문서도 갱신한다.
- 사용자가 커밋·푸시를 요청했거나 작업 완료 시 커밋·푸시를 지시한 범위에서는, 추가 확인 없이 해당 프로젝트의 현재 브랜치에 즉시 커밋·푸시한다.
- Git 표준 흐름은 **로컬 구현·검증 → `facs` 커밋·푸시 → 사용자 수동 검증 → 사용자 `적합` 판정 → `main` 반영 여부를 사용자에게 확인 → `main` 병합·푸시 → 운영 배포 확인** 순서다. `main`에는 `facs`에서 먼저 검증·푸시된 변경만 반영하며, 이 순서를 생략하지 않는다.
- 불명확하거나 서로 충돌하는 요구는 임의로 구현하지 않고, 먼저 이 문서에 반영할 정책 결정을 제안한다.
- 사용자에게 보이는 문구는 비판단적이고 존중하는 언어를 사용한다.
- 전체 기능 범위와 상태는 `feature-backlog.md`에서 관리한다. 새 기능은 해당 문서에 기록한 뒤 구현한다.
- 사용자 기능을 새로 정의하거나 변경할 때는, 해당 기능의 관리자 설정·조회·제어·모니터링·감사 요구를 함께 분석해 관리자 기능 목록을 같은 작업 흐름에서 갱신한다.
- 각 개발 단계는 사용자 수동 검증과 명시적 `적합` 확인을 받아야 완료로 처리한다. 적합 확인 전에는 다음 단계로 진행하지 않는다.
- 정책 결정 단계와 구현 단계 모두 과제를 한 번에 하나씩 사용자에게 제시하고, 답변 또는 검증 결과를 기록한 뒤에만 다음 과제로 진행한다.
- 구현 단계가 사용자에게서 `적합` 판정을 받으면, 검증된 변경을 로컬 개발 소스에 반영한다. Chrome 로컬 미리보기는 사용자가 `로컬에 라이브해줘`처럼 명시적으로 요청한 경우에만 실행하며, 코드 변경·빌드 성공만으로 자동 실행하지 않는다. 이 확인이 끝난 뒤에만 다음 단계로 진행한다.
- 사용자 검증용 미리보기는 이전 탭·번들·서비스 워커의 캐시 영향을 받지 않게 제공한다. 매 검증마다 고유 개발 서버 포트와 변경 식별 쿼리를 사용하고, 해당 서버가 최신 소스 번들을 실제 제공하는지 확인한 뒤 링크를 전달한다.


## 9. 범위와 비목표

### 이번 서비스 범위

- 사진 기반의 첫인상 질문과 익명 또는 준익명 YES/NO 반응을 제공한다.
- 업로더에게 누적 결과와 카테고리별 요약을 제공한다.
- 운영자는 공개 전·후 콘텐츠를 검토하고 신고를 처리한다.

### 비목표

- 심리 진단, 채용 적합성 판정, 연애·외모에 대한 객관적 등급 판정을 제공하지 않는다.
- 개인 간 직접 연락, 공개 댓글, 외부 SNS 공유는 안전 정책과 운영 역량이 준비되기 전에는 제공하지 않는다.
- AI가 얼굴·인종·성별·나이·건강 상태 등 민감한 특성을 추론하거나 평가하지 않는다.

## 10. 콘텐츠와 투표의 생명주기

### Post 상태

`draft → submitted → under_review → published → archived/deleted`

- `draft`: 업로더만 볼 수 있다.
- `submitted`: 업로드 검증이 끝나면 검토 대기 상태가 된다.
- `under_review`: 자동 또는 운영 검토 중이며 피드에 노출하지 않는다.
- `published`: 정책을 통과해 투표 피드와 결과 화면에 노출할 수 있다.
- `archived`: 공개 노출은 중단하되, 보존 정책에 따라 최소 기록만 유지할 수 있다.
- `deleted`: 원본 이미지와 공개 데이터는 삭제 요청·보존 정책에 따라 처리한다.

### Vote 규칙

- 인증된 사용자당 동일 카드에는 하나의 유효 투표만 허용한다.
- 선택값 변경 허용 여부와 변경 가능 시간은 API 정책으로 명시한다. 기본값은 **변경 불가**다.
- 투표는 서버 시간이 기준이며, 클라이언트가 보낸 집계값을 신뢰하지 않는다.
- 차단·삭제·검토 대상 카드의 투표는 새로 받을 수 없고, 집계 노출 여부를 명확히 한다.
- 자동화·반복 투표가 의심되면 속도 제한, 위험 점수, 검토 대기 정책을 적용한다.

## 11. 결과·랭킹 정의

- **긍정률** = YES / (YES + NO) × 100.
- 결과 화면에는 총 유효 투표 수와 표본 부족 상태를 함께 표시한다.
- 랭킹 후보는 최소 유효 투표 수, 최근성, 이상 투표 제외 여부를 모두 충족해야 한다.
- 랭킹의 정확한 최소 표본 수·노출 기간·동점 처리 규칙은 출시 전 수치로 결정해 이 문서에 기록한다.
- 신뢰도 점수의 공식·가중치는 사용자에게 오해를 주지 않도록 설명 가능해야 하며, 점수 조작을 유도할 정도로 상세한 탐지 규칙은 공개하지 않는다.

## 12. 데이터·API 계약 기준

- 모든 리소스는 불변 ID, 생성·수정 시각, 상태, 소유자 정보를 갖는다.
- API는 페이지네이션, 정렬, 필터 조건과 표준 오류 코드(`400/401/403/404/409/429`)를 일관되게 제공한다.
- 쓰기 요청에는 중복 제출 방지를 위한 idempotency key를 지원한다.
- Post, Vote, Aggregate의 집계 갱신은 서버 트랜잭션 또는 재처리 가능한 이벤트 흐름으로 보장한다.
- 삭제 요청·운영 조치·권한 변경은 감사 로그에 주체, 시간, 대상, 사유를 남긴다.
- 외부에 노출되는 이미지 URL은 짧은 수명의 서명 URL 또는 권한 확인을 거친 프록시를 사용한다.

## 13. 보안·개인정보·운영 기준

- 인증 세션은 안전한 저장 방식과 만료·로그아웃·재인증 정책을 갖는다.
- 역할은 최소 권한 원칙으로 분리한다: 일반 사용자, 운영자, 관리자.
- 원본 이미지·EXIF 위치 정보·식별 가능한 메타데이터는 공개 전 제거 또는 비공개 처리한다.
- 신고에는 유형, 설명, 증거, 처리 상태를 남기고, 운영자는 처리 사유와 재검토 경로를 제공한다.
- 서비스 출시 전 개인정보 처리방침, 이용약관, 콘텐츠 정책, 삭제·보존 기간, 미성년자 보호 정책을 확정한다.
- 비밀값은 저장소·클라이언트·로그에 기록하지 않고 배포 환경의 비밀 관리 기능으로만 주입한다.

## 14. 품질·접근성·운영 관측

- 모바일 우선으로 설계하고 키보드 탐색, 충분한 색상 대비, 대체 텍스트, 화면 낭독기 레이블을 제공한다.
- 반응형 웹은 서비스의 기본 규칙이다. 모든 화면은 사용 장비·해상도·브라우저의 실제 가용 뷰포트에 맞춰 유연하게 배치한다. 스마트폰은 좌우 여백 없이 전체 폭을 사용하고, 태블릿·PC는 일반 SNS처럼 여백 안의 중앙 콘텐츠 컬럼(최대 640px)을 사용한다. 고정 폭 캔버스를 화면에 축소해 끼워 넣는 방식은 사용하지 않는다.
- 어떤 화면 크기에서도 카드는 상단 헤더 아래부터 하단 메뉴 위까지의 가용 영역을 정확히 채운다. 카드가 잘리거나 내부 스크롤이 생기면 안 되며, 카드와 상·하단 고정 메뉴 사이에 의도되지 않은 여백이 생기면 안 된다.
- Feed를 제외한 Upload·Ranking·Profile 화면은 본문 영역만 세로 스크롤한다. 하단 메뉴는 항상 화면에 고정하고, 본문 마지막 요소가 메뉴에 가려지지 않도록 하단 안전 여백을 둔다.
- 카드의 사진은 서비스가 제공하는 질문·투표·댓글 UI로 넓게 가리지 않는다. 사진·동영상 영역과 평가·댓글 영역을 분리하고, 미디어는 왜곡하거나 해상도 변화 때문에 잘라 보이지 않게 `object-fit: contain`을 우선 사용한다.
- 다중 미디어 카드에는 현재 미디어를 보여 주는 앨범 막대와 좌·우 스와이프를 제공한다. 다음·이전 미디어는 양끝의 좁은 미리보기와 짧은 반동 애니메이션으로 안내하되, 중앙 미디어의 크기를 줄이거나 미디어 간 간격을 넓히지 않는다.
- 피드 카드의 오른쪽 이전·다음 화살표는 PC·모바일 모두에서 항상 제공한다. 모바일은 카드 영역의 위·아래 스와이프로, PC는 카드 영역의 마우스 휠 위·아래 동작으로 이전·다음 카드를 이동한다.
- 하나의 게시물은 최대 이미지 5개와 동영상 1개를 정렬된 미디어 목록으로 보유한다. 카드 상단의 앨범 막대는 전체 개수와 현재 미디어를 나타내며, 막대 클릭 또는 카드 영역의 좌·우 스와이프로 같은 카드 안의 이전·다음 미디어를 전환한다. 세로 카드 탐색과 가로 미디어 탐색은 방향 우선순위로 충돌 없이 구분한다.
- 업로드 실패, 네트워크 지연, 빈 피드, 권한 거부, 검토 대기 상태에 각각 이해 가능한 UI를 제공한다.
- 핵심 지표는 등록 완료율, 첫 투표 완료율, 재방문율, 신고율, 검토 처리 시간, 오류율로 정의한다.
- 운영 환경에는 오류 추적, 구조화 로그, 성능 지표, 알림, 백업·복구 검증을 둔다.
- 데이터 모델·API·랭킹 규칙 변경은 마이그레이션 계획과 롤백 기준을 먼저 정의한다.

### 즉시 실행 규칙

- **P1이 하나라도 미결정이면** 인증·실제 이미지 업로드·공개 피드·투표 API를 구현하지 않는다. 대신 UI 프로토타입, 테스트 데이터, 접근성 개선, API 인터페이스 초안까지만 진행한다. 현재 P1은 모두 완료 상태다.
- 다음 개발 작업을 시작하기 전에 해당 작업과 연결된 P1/P2 항목을 확인하고, 미결정이면 이 채팅에 `🚨 개발 결정 필요` 알림을 표시한다.
- P1 확정 후 구현 순서는 **인증/권한 → 업로드·검토 → 투표·집계 → 결과·랭킹**으로 한다.
- 결정이 완료되면 표의 `결정 완료 기준`을 실제 결정 내용과 날짜로 바꾸고, 결정 기록에도 추가한다.

- 이 문서는 제품 요구사항의 기준이며, 코드·README·배포 설정과 불일치하면 불일치를 먼저 해결한다.
- P1 또는 다음 개발 단계에 필요한 P2 항목이 미결정인 사실을 확인하면, 사용자에게 `🚨 개발 결정 필요` 알림을 먼저 보낸다.
- 이 문서는 제품·정책·도메인 규칙의 **단일 기준(Source of Truth)** 이다. 이 문서가 변경되면 `TECH-AGENTS.md`에서 기술 영향, 코드 구조, API·데이터·보안 규칙을 같은 변경 흐름에서 반드시 갱신한다.
- 확정된 정책도 고정하지 않는다. 운영 지표, 신고·검토 결과, 사용자 피드백, 법·플랫폼 요구사항을 계속 검토하고, 변경 필요 또는 전환 조건 충족 시 사용자에게 알린 뒤 적합 확인을 받아 문서와 구현을 갱신한다.

## 18. 현재 프로토타입 UI 기준

- 현재 사용자 검증 기준 화면은 기존 HTML/CSS/Vanilla JavaScript 피드다. Vite 개발 서버는 이 엔트리 포인트를 제공한다.
- 메인 피드 상단은 **좌측 카테고리 / 우측 사용자 ID** 순서를 기본으로 하며, 질문은 그 아래에 표시한다.
- 기본 샘플 카드는 기존 로컬 이미지 자산을 사용한다. 브라우저 저장 데이터가 샘플을 대체하지 않도록 별도 저장소 키를 사용한다.
- 카테고리별 테마는 피드 헤더, 카테고리 배지, 탐색 제어, YES/NO 투표 제어, YES 결과 막대에 동일하게 적용한다.
- 카드의 외곽선은 직각이 아닌 작은 라운드(`rounded-xl`)를 사용한다.
- 이 UI 기준은 수동 검증이 완료될 때까지 유지한다. 기능·React 전환·디자인을 포함한 다음 변경은 사용자 검증 결과 또는 별도 요청 후에만 진행한다.
